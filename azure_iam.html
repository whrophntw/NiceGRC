GRC Operations > Azure IAM

"IAM" here means the identity and access layer of Microsoft Azure: Entra ID (formerly Azure AD), Azure RBAC role assignments, and the PIM/MFA guardrails around privileged access. The compliance problem is not that these controls do not exist — it is that proving them usually means a human clicking through the portal and exporting spreadsheets by hand. The agent removes the clicking.

The split that matters: read vs. write

Before a single command runs, the workflow draws a hard line. The Azure MCP server is read-only — it queries the Resource Graph and policy state and produces evidence. Actual changes — creating a role assignment, enforcing a policy — go through the az CLI. Two tools, two different trust levels:

mcp_azure_arm   command=execute_query     # read-only evidence
az role assignment create ...             # real, audited change

This is the guardrail that keeps evidence gathering from mutating the very environment it is auditing.

Step one: enumerate what already exists

The agent pulls every role assignment in the subscription with a Resource Graph query:

AuthorizationResources
| where type == 'microsoft.authorization/roleassignments'
| project principalId, roleDefinitionId, scope

That flat list — who, what role, at what scope — is the raw material for a least-privilege review. No more screenshots of the portal.

Step two: map it to a control

A list of role assignments means nothing to an auditor until it maps to a requirement. Two ISO 27001:2022 controls cover this ground:

  • A.5.15 (Access control) — RBAC + least-privilege, joiners/movers/leavers fed by a HR process. Evidence: the role assignment export, access review records.
  • A.8.2 (Privileged access rights) — PIM and MFA enforced on write/delete actions. Evidence: the "MFA for Resource Write Actions" and "MFA for Resource Delete Actions" policy assignments.

Step three: tighten, don't surprise

Writes are proposed first. The agent drafts the az role assignment delete or the PIM elevation change, states which control it serves, and asks before it touches anything. Automation that silently rewrites your IAM is not automation — it is an incident with a nice UI.

Where it stands

In the current lab, A.5.15 is assessed as implemented and A.8.2 as partial (PIM rollout in progress). The evidence is real; the gaps are stated as gaps. That honesty is the whole point of the workflow.
